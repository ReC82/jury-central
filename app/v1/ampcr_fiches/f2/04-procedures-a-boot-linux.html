3.A (suite) Démarrage : GRUB, Linux, BitLocker

P1.5 — GRUB : « grub rescue> », menu absent, PC qui démarre toujours Windows, Windows absent du menu

Fréquence : fréquent en double démarrage · Gravité : bloquante pour Linux, données intactes

1. Symptômes observables

  • error: no such partition. / error: unknown filesystem. puis invite grub rescue>.
  • Minimal BASH-like line editing is supported… puis grub> : GRUB n'a pas trouvé son grub.cfg (moins grave que grub rescue>).
  • Après installation de Linux, le PC démarre directement Windows ; ou, après une MAJ de Windows, GRUB n'apparaît plus.
  • Menu GRUB présent mais sans « Windows Boot Manager ».

2. Causes possibles (classées)

  1. Ordre UEFI : Windows Boot Manager remis en tête (MAJ Windows, bcdboot, reset firmware) — configuration.
  2. os-prober désactivé (GRUB 2.06 et suivants) → Windows non détecté par update-grub — configuration.
  3. Linux installé dans un mode différent de Windows (Linux en hérité, Windows en UEFI) — installation.
  4. Partition Linux supprimée/redimensionnée/déplacée depuis Windows (Gestion des disques) → grub rescue> — partitions.
  5. ESP abîmée, disque changé — partitions/matériel.

3. Questions initiales et sécurité

  • Quelqu'un a-t-il « fait de la place » ou supprimé une partition « sans lettre » depuis Windows ?
  • Clé live de la même distribution disponible ? Sauvegarde de /home si la partition est endommagée.
  • Ne jamais formater l'ESP : elle porte aussi le chargeur de Windows.

4. Diagnostic pas à pas

  1. Menu de démarrage ponctuel (F12/F11/F8/Échap) : une entrée « ubuntu » (ou « debian ») existe-t-elle ?

    SI oui et elle démarre GRUB → seul l'ordre est en cause : la mettre en tête dans le setup, ou sous Linux sudo efibootmgr -o 0001,0000.

    SINON → étape 2.

  2. Si GRUB démarre mais Windows manque : grep OS_PROBER /etc/default/grub.

    SI absent ou true → ajouter GRUB_DISABLE_OS_PROBER=false, sudo update-grub ; la sortie doit contenir « Found Windows Boot Manager on /dev/nvme0n1p1@/EFI/Microsoft/Boot/bootmgfw.efi ».

    SINON (os-prober actif, Windows toujours absent) → modes différents : [ -d /sys/firmware/efi ] && echo UEFI || echo BIOS sous Linux, msinfo32 sous Windows ; les deux doivent être en UEFI.

  3. À l'invite grub rescue> : localiser la partition Linux : ls puis ls (hd0,gpt3)/ sur chaque partition.

    SI une partition affiche boot/ etc/ home/ → démarrage manuel (commandes ci-dessous), puis réinstallation propre de GRUB depuis Linux démarré.

    SINON (« Filesystem is unknown » partout) → partition supprimée/écrasée : clé live, lsblk -f ; récupération de données (testdisk) avant toute réinstallation.

  4. Si Linux ne démarre pas du tout : réparer depuis une session live (chroot, commandes ci-dessous).
grub rescue> ls
(hd0) (hd0,gpt1) (hd0,gpt2) (hd0,gpt3)
grub rescue> ls (hd0,gpt3)/
grub rescue> set root=(hd0,gpt3)
grub rescue> set prefix=(hd0,gpt3)/boot/grub
grub rescue> insmod normal
grub rescue> normal

Puis, une fois Linux démarré : sudo grub-install (UEFI : sans argument de disque sur Ubuntu) et sudo update-grub.

ubuntu@live:~$ lsblk -f                         # repérer ESP (vfat) et racine (ext4)
ubuntu@live:~$ sudo mount /dev/nvme0n1p3 /mnt
ubuntu@live:~$ sudo mount /dev/nvme0n1p1 /mnt/boot/efi
ubuntu@live:~$ for d in dev proc sys run; do sudo mount --rbind /$d /mnt/$d; done
ubuntu@live:~$ sudo chroot /mnt
root@live:/# grub-install --target=x86_64-efi --efi-directory=/boot/efi --bootloader-id=ubuntu
root@live:/# update-grub
root@live:/# exit
Installing for x86_64-efi platform.
Installation finished. No error reported.
...
Found linux image: /boot/vmlinuz-6.8.0-45-generic
Found Windows Boot Manager on /dev/nvme0n1p1@/EFI/Microsoft/Boot/bootmgfw.efi
done

Démarrage hérité (BIOS/MBR) : grub-install /dev/sda — le disque, jamais une partition (/dev/sda1). Fedora : grub2-mkconfig -o /boot/grub2/grub.cfg au lieu de update-grub.

Attention Monter la bonne partition en /mnt/boot/efi : l'ESP (vfat, 100–550 Mo), jamais la partition Windows. Prérequis : lsblk -f lu, sauvegarde de /home si doute. Alternative prudente : démarrer Linux via l'entrée « ubuntu » du menu ponctuel ou via grub rescue> manuel, puis réparer depuis le système démarré.

5. Test de confirmation

Le menu GRUB s'affiche au démarrage à froid et liste Linux et Windows ; chaque entrée démarre. Limite : une MAJ de Windows peut de nouveau changer l'ordre (prévenir l'utilisateur).

6. Correction

  1. Ordre UEFI (setup ou efibootmgr -o) ;
  2. os-prober + update-grub ;
  3. grub-install + update-grub (live + chroot) ;
  4. réinstallation de Linux dans le même mode que Windows si les modes diffèrent (sauvegarde de /home).

7. Validation

  • Deux démarrages à froid ; chaque système démarre depuis GRUB ; sudo efibootmgr : BootOrder commence par l'entrée ubuntu.

8. Réponse d'examen modèle

Réponse rédigée attendue

Après l'installation d'Ubuntu à côté de Windows 11, le PC démarre directement Windows. Hypothèses : 1) Windows Boot Manager est resté prioritaire dans l'ordre UEFI ; 2) Ubuntu a été installé en mode hérité ; 3) GRUB n'a pas été installé. Test 1 : menu de démarrage ponctuel → l'entrée « ubuntu » existe et affiche GRUB : hypothèse 1 confirmée. Correction : je place « ubuntu » en tête de l'ordre de démarrage (réglage firmware réversible). Si Windows manquait dans GRUB, j'activerais GRUB_DISABLE_OS_PROBER=false puis sudo update-grub. Validation : deux démarrages à froid, les deux systèmes démarrent ; je préviens l'utilisateur qu'une mise à jour de Windows peut modifier l'ordre.

Perd des points : réinstaller Ubuntu ; bootrec /fixmbr (efface GRUB en hérité, inutile en UEFI) ; grub-install /dev/sda1.

9. Pièges et variantes

Piège Supprimer depuis la Gestion des disques de Windows une partition « inconnue » ou « sans lettre » : c'était Linux ou l'ESP. Aucune partition sans lettre ne se supprime sans lsblk -f/inventaire.
  • Linux voit la partition Windows en lecture seule (« The disk contains an unclean file system (0, 0). Metadata kept in Windows cache, refused to mount. ») → Démarrage rapide de Windows actif : le désactiver (Panneau de configuration → Options d'alimentation → Choisir l'action des boutons d'alimentation → Modifier des paramètres actuellement non disponibles → décocher « Activer le démarrage rapide »).
  • « Verification failed: (0x1A) Security Violation » au lancement de GRUB : Secure Boot et chargeur non signé/révoqué (SBAT) → mettre à jour shim/GRUB ou désactiver temporairement Secure Boot (attention BitLocker).

P1.6 — Linux : « (initramfs) », « You are in emergency mode », « UNEXPECTED INCONSISTENCY; RUN fsck MANUALLY »

Fréquence : fréquent · Gravité : bloquante, réparable sans perte dans la majorité des cas

1. Symptômes observables

  • Gave up waiting for root file system device. … ALERT! UUID=3f2a… does not exist. Dropping to a shell! puis (initramfs).
  • /dev/sda2: UNEXPECTED INCONSISTENCY; RUN fsck MANUALLY. (i.e., without -a or -p options) puis (initramfs).
  • [ TIME ] Timed out waiting for device /dev/disk/by-uuid/…, [DEPEND] Dependency failed for Local File Systems., puis You are in emergency mode. After logging in, type "journalctl -xb" to view system logs… ; parfois « Cannot open access to console, the root account is locked. »

2. Causes possibles (classées)

  1. Ligne de /etc/fstab : disque de données retiré, UUID changé après remplacement/formatage, faute de frappe — configuration.
  2. Système de fichiers incohérent après arrêt brutal — stockage logique.
  3. Disque/contrôleur non vu (mode RAID/VMD changé, câble) — firmware/matériel.
  4. initramfs incomplet après MAJ interrompue — OS (P3.4).

3. Questions initiales et sécurité

  • Disque ajouté, remplacé, retiré récemment ? Coupure de courant ?
  • Avant toute modification de fstab : copie /etc/fstab.bak. fsck uniquement sur un système de fichiers non monté.

4. Diagnostic pas à pas

  1. Lire le message : (initramfs) avec ALERT UUID, avec INCONSISTENCY, ou mode d'urgence ?

    SI INCONSISTENCY → étape 2.

    SINON SI ALERT UUID → étape 3 ; SINON (emergency mode) → étape 4.

  2. Dans (initramfs) : fsck /dev/sda2 (le périphérique cité ; il n'est pas monté à ce stade), répondre aux questions ou fsck -y, puis exit. — attendu : « FILE SYSTEM WAS MODIFIED », démarrage reprend.

    SI fsck répète des erreurs ou signale des erreurs de lecture → disque qui faiblit : sauvegarde depuis une clé live, SMART (Fiche 1).

    SINON valider.

  3. Dans (initramfs) : blkid et ls /dev/sd* /dev/nvme*. — comparer l'UUID affiché par l'ALERT à ceux listés.

    SI le disque n'apparaît pas → mode du contrôleur dans le firmware (VMD/RAID) ou matériel (Fiche 1).

    SINON (disque présent, UUID différent) → racine reformatée/clonée : démarrer une live, corriger /etc/fstab et lancer update-grub + update-initramfs -u en chroot (cf. P1.5).

  4. Mode d'urgence : se connecter (mot de passe root) puis journalctl -xb | grep -iE 'fail|mount', ou systemctl --failed. — repérer l'unité .mount en échec (ex. data.mount).

    SI root verrouillé (Ubuntu) → démarrer via GRUB → Advanced options → (recovery mode) → root, ou clé live.

    SINON → étape 5.

  5. Comparer fstab et la réalité : cat /etc/fstab et lsblk -f.

    SI UUID de fstab absent de lsblk -f → disque retiré ou remplacé : corriger l'UUID ou commenter la ligne, ajouter nofail pour un disque non indispensable.

    SINON → type/option erronés (ext4 vs ntfs, faute dans les options) : corriger.

root@pc:~# mount -o remount,rw /
root@pc:~# cp /etc/fstab /etc/fstab.bak
root@pc:~# lsblk -f
root@pc:~# nano /etc/fstab
root@pc:~# findmnt --verify
root@pc:~# systemctl daemon-reload
root@pc:~# mount -a
NAME        FSTYPE LABEL UUID                                 MOUNTPOINTS
sda
└─sda1      ext4   data  9b1c7e2d-5a40-4c1e-8f7e-2d0c6b1e44aa
nvme0n1
├─nvme0n1p1 vfat         4C2E-91AB                            /boot/efi
└─nvme0n1p2 ext4         3f2a8d10-77c1-4f0b-9a55-6e3d2c1b0f12 /

# /etc/fstab (ligne fautive puis corrigée)
UUID=0d4e5f61-aaaa-4b2c-9d8e-112233445566 /data ext4 defaults 0 2
UUID=9b1c7e2d-5a40-4c1e-8f7e-2d0c6b1e44aa /data ext4 defaults,nofail 0 2

Attention fsck sur un système de fichiers monté en écriture peut le détruire : uniquement depuis (initramfs), le mode recovery (racine en lecture seule) ou une clé live. fsck peut déplacer des fichiers abîmés dans lost+found. Prérequis : sauvegarde si le disque est suspect. Alternative prudente : monter en lecture seule depuis une live et copier les données d'abord.

5. Test de confirmation

findmnt --verify sans erreur et mount -a silencieux avant de redémarrer ; puis démarrage normal. Limite : mount -a ne teste pas la racine.

6. Correction

UUID corrigé / ligne commentée / nofail ; fsck sur partition démontée ; régénération de l'initramfs si pilote ou UUID de racine changé (sudo update-initramfs -u).

7. Validation

  • Redémarrage complet sans mode d'urgence ; findmnt /data montre le montage ; systemctl --failed : 0 unité ; journalctl -b -p err sans erreur de montage.

8. Réponse d'examen modèle

Réponse rédigée attendue

Le message « Dependency failed for Local File Systems » suivi du mode d'urgence indique qu'un montage déclaré dans /etc/fstab a échoué ; le noyau et la racine fonctionnent. Comme le disque de données a été remplacé hier, je suppose que l'UUID de fstab est celui de l'ancien disque. Test : journalctl -xb montre l'échec de data.mount sur /dev/disk/by-uuid/0d4e… ; lsblk -f montre que le nouveau disque a l'UUID 9b1c…. Correction : mount -o remount,rw /, copie de sauvegarde de fstab, remplacement de l'UUID, ajout de nofail (disque non indispensable), test findmnt --verify puis mount -a. Validation : redémarrage normal, /data monté, aucune unité en échec.

Perd des points : formater ou réinstaller ; fsck sur une partition montée ; modifier fstab sans copie ni test avant redémarrage ; utiliser /dev/sdb1 au lieu de l'UUID (le nom peut changer).

9. Pièges et variantes

  • « Read-only file system » en mode d'urgence : normal, d'où mount -o remount,rw /.
  • Clé USB/disque externe dans fstab sans nofail : mode d'urgence dès qu'elle est absente.
  • Faute de frappe dans une ligne de partage réseau (cifs/nfs) : ajouter _netdev,nofail.

P1.7 — Écran « Récupération BitLocker » / « Entrez la clé de récupération pour ce lecteur »

Fréquence : assez fréquent sur portables récents · Gravité : critique (perte de données si la clé est introuvable)

1. Symptômes observables

  • Écran bleu de saisie : « Entrez la clé de récupération pour ce lecteur », avec un ID de clé (8 premiers caractères) et l'adresse d'aide aka.ms/myrecoverykey.
  • Contexte : MAJ du BIOS, Secure Boot désactivé, TPM effacé, ordre de démarrage changé, carte mère remplacée, disque déplacé, clé USB laissée branchée sur certains modèles.

2. Causes possibles (classées)

  1. Changement de la configuration mesurée par le TPM (firmware, Secure Boot, ordre) — configuration.
  2. TPM effacé/remplacé (carte mère) — matériel/configuration.
  3. Tentatives de code PIN erronées — utilisateur.

3. Questions initiales et sécurité

  • Compte Microsoft de l'utilisateur ? PC d'entreprise (clé dans Active Directory/Entra ID, chez l'administrateur) ? Clé imprimée/enregistrée sur clé USB ?
  • Ne jamais réinitialiser/réinstaller « pour passer l'écran » : sans clé, les données sont perdues.

4. Diagnostic pas à pas

  1. Annuler le dernier changement firmware (réactiver Secure Boot, remettre l'ordre, retirer la clé USB). — attendu : démarrage sans demande de clé.

    SI OK → valider ; suspendre BitLocker avant de refaire le changement voulu.

    SINON → étape 2.

  2. Récupérer la clé de 48 chiffres correspondant à l'ID affiché : compte Microsoft (sur un autre appareil, page des clés de récupération), administrateur du domaine, impression.

    SI trouvée → la saisir.

    SINON → escalade, informer le client : données inaccessibles ; pas d'autre recours technique légitime.

5. Test de confirmation

Le démarrage suivant ne redemande pas la clé ; manage-bde -status C: → « Protection activée ».

6. Correction

Après saisie : depuis Windows, manage-bde -protectors -enable C: si la protection est suspendue. Avant toute future MAJ BIOS/changement Secure Boot : Panneau de configuration → Chiffrement de lecteur BitLocker → Suspendre la protection (ou manage-bde -protectors -disable C: -RebootCount 1). Dans WinRE, déverrouiller avant toute commande : manage-bde -unlock C: -RecoveryPassword 123456-….

7. Validation

  • Deux redémarrages sans demande ; clé de récupération sauvegardée en lieu sûr et notée dans le rapport (son emplacement, pas la clé elle-même).

8. Réponse d'examen modèle

Réponse rédigée attendue

L'écran de récupération BitLocker est apparu après la mise à jour du BIOS : le TPM ne reconnaît plus la configuration de démarrage et protège le disque chiffré. Ce n'est pas une panne du disque. Je récupère la clé de récupération (48 chiffres) correspondant à l'ID affiché dans le compte Microsoft du client, je la saisis, puis je vérifie manage-bde -status. Pour les prochaines mises à jour du firmware, je suspends la protection BitLocker avant l'opération. Sans clé, j'informe le client que les données ne sont pas récupérables et je n'efface rien sans son accord écrit.

Perd des points : proposer de réinstaller ; ignorer l'existence du chiffrement avant de changer Secure Boot/mode de démarrage.

9. Pièges et variantes

  • Windows 11 Famille : « Chiffrement de l'appareil » (même mécanisme, même clé dans le compte Microsoft).
  • Dans WinRE, le volume chiffré apparaît sans système de fichiers lisible : ce n'est pas un volume RAW abîmé.

P1.8 — Linux : écran noir après GRUB, ou retour à l'écran de connexion en boucle

Fréquence : assez fréquent · Gravité : moyenne (système fonctionnel en console)

1. Symptômes observables

  • Écran noir ou curseur clignotant après le logo ; ou mot de passe accepté puis retour à l'écran de connexion (boucle de connexion).
  • Contexte : installation du pilote NVIDIA propriétaire, MAJ du noyau, Secure Boot actif, disque plein, commande graphique lancée avec sudo.

2. Causes possibles (classées)

  1. Pilote graphique : module non chargé (Secure Boot sans inscription de clé MOK), pilote incompatible avec le nouveau noyau.
  2. /home ou / plein (la session ne peut écrire).
  3. Fichiers de session appartenant à root (~/.Xauthority, ~/.config) après un sudo graphique.

3. Questions initiales et sécurité

  • Tous les comptes ou un seul ? Après quelle installation ?

4. Diagnostic pas à pas

  1. Ctrl+Alt+F3 → console texte, connexion.

    SI la console fonctionne → le système tourne ; étape 2.

    SINON → GRUB, touche e sur l'entrée, ajouter nomodeset à la ligne linux, Ctrl+X (test temporaire).

  2. df -h.

    SI / ou /home à 100 % → P5.6.

    SINON → étape 3.

  3. Un seul compte en boucle ? ls -la ~ | grep root.

    SI .Xauthority ou .config à root → sudo chown -R nom:nom /home/nom/.Xauthority /home/nom/.config.

    SINON → pilote : journalctl -b -p err, lsmod | grep -E 'nvidia|nouveau', mokutil --sb-state.

5. Test de confirmation

Le démarrage avec nomodeset ou sur l'ancien noyau donne une session → pilote/noyau confirmé. Limite : nomodeset désactive l'accélération, c'est un contournement.

6. Correction

Ubuntu : ubuntu-drivers devices puis sudo ubuntu-drivers install (pilote recommandé) ; avec Secure Boot, accepter l'inscription de la clé MOK au redémarrage (écran bleu « Perform MOK management » → Enroll MOK) ; sinon revenir au pilote libre (sudo apt purge 'nvidia-*' après avoir noté les paquets).

7. Validation

  • Deux connexions graphiques, nomodeset retiré, nvidia-smi ou paramètres d'affichage corrects.

8. Réponse d'examen modèle

Réponse rédigée attendue

La console (Ctrl+Alt+F3) fonctionne : le système démarre, seule la session graphique échoue. Je vérifie l'espace (df -h) puis le journal du démarrage (journalctl -b -p err), qui montre que le module nvidia n'est pas chargé ; mokutil --sb-state indique Secure Boot activé. Cause : pilote propriétaire non signé. Correction : réinstallation du pilote recommandé avec inscription de la clé MOK. Validation : session graphique ouverte deux fois.

9. Pièges et variantes

  • Écran noir seulement sur l'écran externe : câble/entrée de l'écran, pas l'OS.
