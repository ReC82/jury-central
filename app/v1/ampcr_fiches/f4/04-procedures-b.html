3 B. Procédures : passerelle, DNS, Internet, pare-feu, lenteurs

P3.6 — Réseau local OK, Internet KO même par adresse IP (un seul poste)

Fréquence : fréquent (configuration manuelle, Linux installé à la main) · Gravité : bloquante pour l'accès Internet

1. Symptômes observables

  • Le poste ouvre le NAS / le partage local, pinge la box ou un voisin, mais ping 8.8.8.8 échoue ; les autres postes ont Internet.
  • Windows : « Passerelle par défaut » vide ou fausse ; ping 8.8.8.8 → « PING : échec de la transmission. Défaillance générale. » (pas de route) ou « Délai d'attente » (passerelle fausse mais existante).
  • Linux :
    $ ip route
192.168.50.0/24 dev enp3s0 proto kernel scope link src 192.168.50.40 metric 100
$ ping -c 2 8.8.8.8
ping: connect: Network is unreachable

2. Causes possibles (classées)

  1. Passerelle non saisie (configuration statique incomplète).
  2. Passerelle erronée : adresse d'un autre appareil (NAS, imprimante), ancienne box, faute de frappe.
  3. Passerelle hors du réseau du poste (masque faux → P3.5).
  4. Deux cartes actives avec deux passerelles (Wi-Fi + Ethernet sur des réseaux différents, VPN) : métrique qui envoie le trafic au mauvais endroit.
  5. Filtrage sur la box (contrôle parental, blocage par MAC de ce poste).

3. Questions initiales et sécurité

  • « Poste en adresse fixe ? Installé récemment ? Un VPN ? » Relever la configuration avant modification.

4. Diagnostic pas à pas

  1. ipconfig / ip route — attendu : passerelle = IP LAN du routeur (plan), ligne default via 192.168.50.1 dev enp3s0.

    SI vide / pas de default via → cause confirmée : passerelle manquante.

    SINON → étape 2.

  2. ping de la passerelle configurée.

    SI pas de réponse, ou elle répond mais arp -a montre une MAC qui n'est pas celle de la box → passerelle erronée (autre appareil).

    SINON (la vraie box répond) → étape 3.

  3. tracert -d 8.8.8.8 — attendu : saut 1 = box, puis routeurs du FAI.

    SI saut 1 = autre adresse (VPN 10.8.0.1, Wi-Fi d'un autre réseau) → table de routage / métriques : route print.

    SINON (s'arrête après la box alors que les voisins passent) → filtrage spécifique au poste sur la box.

5. Test de confirmation

Ajout temporaire de la route par défaut : Windows route add 0.0.0.0 mask 0.0.0.0 192.168.50.1 ; Linux sudo ip route add default via 192.168.50.1 → ping 8.8.8.8 répond. Limite : ces ajouts ne survivent pas au redémarrage (ou à la reconnexion), ce n'est pas la correction.

6. Correction

  • Windows : propriétés IPv4 → Passerelle par défaut 192.168.50.1 (ou repasser en DHCP) ; netsh interface ipv4 set address name="Ethernet" static 192.168.50.40 255.255.255.0 192.168.50.1.
  • Linux : Paramètres → Réseau → IPv4 manuel → Passerelle, ou nmcli con mod "Connexion filaire 1" ipv4.gateway 192.168.50.1 ipv4.dns 192.168.50.10 puis nmcli con up "Connexion filaire 1" (Debian sans NetworkManager : ligne gateway 192.168.50.1 dans /etc/network/interfaces, puis sudo systemctl restart networking).
  • Deux cartes : désactiver celle qui ne sert pas, ou ajuster la métrique.

7. Validation

ip route : default via 192.168.50.1 dev enp3s0 proto static metric 100 ; ping 8.8.8.8, ping d'un nom ; redémarrer le poste et revérifier (persistance).

8. Réponse d'examen modèle

Réponse rédigée attendue

« ip addr montre 192.168.50.40/24 et le lien UP : l'adressage local est correct, et le NAS (192.168.50.20) répond. ip route ne contient que la route du réseau local, sans ligne “default via” : le poste ne sait pas où envoyer les paquets destinés à l'extérieur, d'où le message “Network is unreachable” (rien n'est émis ; ce n'est pas un délai dépassé). Cause : passerelle non configurée lors de l'installation. Correction durable : dans la connexion NetworkManager, passerelle 192.168.50.1 et DNS 192.168.50.10, puis réactivation de la connexion. Vérification : ip route affiche “default via 192.168.50.1 dev enp3s0”, ping 8.8.8.8 puis ping d'un nom réussissent, et la configuration reste après redémarrage. »

Perd des points : accuser le DNS alors que même l'IP 8.8.8.8 échoue ; proposer uniquement ip route add (non persistant) ; redémarrer la box alors que les autres postes ont Internet.

9. Pièges et variantes

Piège En réseau ISOLÉ (deux PC en direct, mini-réseau sans Internet), une passerelle vide est NORMALE. La passerelle doit être dans le réseau du poste : 192.168.50.1 pour un poste en 192.168.50.0/24 ; écrire 192.168.1.1 « par habitude » est l'erreur classique d'examen.

P3.7 — Ping par adresse OK, noms introuvables (DNS)

Fréquence : très fréquent · Gravité : bloquante pour l'utilisateur (« Internet ne marche pas ») mais réseau sain

1. Symptômes observables

  • ping 8.8.8.8 répond ; ping www.google.be → « La requête Ping n'a pas pu trouver l'hôte www.google.be. Vérifiez le nom et essayez à nouveau. »
  • Navigateur : « Ce site est inaccessible – DNS_PROBE_FINISHED_NXDOMAIN » ou « …_BAD_CONFIG » ; Linux : « Temporary failure in name resolution ».
  • Variante interne : Internet OK mais \\srv01 ou intranet.entreprise.local introuvables.

2. Causes possibles (classées)

  1. Serveur DNS saisi à la main faux ou disparu (ancien serveur, ancienne box).
  2. Poste réglé sur un DNS public (8.8.8.8) dans un réseau à domaine : les noms internes ne sont pas connus des DNS publics.
  3. Serveur DNS interne / box : service arrêté, redirecteurs cassés.
  4. Cache DNS du poste avec une entrée erronée ou négative ; fichier hosts modifié (malware, ancien test).
  5. Nom mal orthographié, enregistrement absent (nom interne jamais créé).
  6. Port 53 bloqué par un pare-feu.

3. Questions initiales et sécurité

  • « Tous les sites ou un seul ? Les noms internes aussi ? Tous les postes ? » Un seul site KO = souvent le site lui-même.

4. Diagnostic pas à pas

  1. Confirmer que la connectivité IP est bonne : ping 8.8.8.8 OK (sinon → P3.6 / P3.8).
  2. ipconfig /all → « Serveurs DNS » ; comparer avec le plan / un poste qui fonctionne.
  3. nslookup www.google.be (utilise le DNS configuré).
    DNS request timed out.
    timeout was 2 seconds.
Serveur :   UnKnown
Address:  192.168.50.5

DNS request timed out.
    timeout was 2 seconds.
*** Le délai de la requête vers UnKnown a expiré

    SI délai expiré → le serveur DNS configuré ne répond pas (n'existe plus, éteint) : étape 4.

    SINON SI « *** srv01 ne parvient pas à trouver www.exemple.be : Non-existent domain » → le serveur répond mais ne connaît pas le nom : nom erroné ou enregistrement manquant (ou serveur DNS public interrogé pour un nom interne).

  4. nslookup www.google.be 1.1.1.1 (force un autre serveur).
    Serveur :   one.one.one.one
Address:  1.1.1.1

Réponse ne faisant pas autorité :
Nom :    www.google.be
Addresses:  2a00:1450:400e:80d::2003
          142.250.179.195

    SI réponse → la résolution fonctionne ailleurs : le serveur DNS configuré est en cause.

    SINON → port 53 filtré (pare-feu, réseau d'entreprise qui impose son DNS).

  5. Si nslookup répond mais le ping de nom échoue → cache local ou fichier hosts : ipconfig /displaydns, type C:\Windows\System32\drivers\etc\hosts (Linux /etc/hosts, resolvectl status).

5. Test de confirmation

nslookup nom serveur_dns_correct donne l'adresse alors que le serveur configuré échoue ; après correction, le ping par nom résout la bonne adresse. Limite : « Réponse ne faisant pas autorité » est NORMAL (le serveur relaie la réponse, il n'est pas propriétaire du domaine) — ce n'est pas une erreur.

6. Correction

  • DNS = celui du plan : en réseau d'entreprise, le serveur DNS interne / contrôleur de domaine (qui relaie Internet) ; en petit réseau, la box (ou DHCP). Repasser en « Obtenir l'adresse des serveurs DNS automatiquement » si le DHCP distribue le bon.
  • Commande (admin) : netsh interface ipv4 set dnsservers name="Ethernet" static 192.168.50.10 primary.
  • Corriger l'option DNS dans le serveur DHCP si TOUS les postes ont la mauvaise valeur, puis ipconfig /renew.
  • ipconfig /flushdns (vide le cache) ; restaurer le fichier hosts ; créer l'enregistrement manquant sur le serveur DNS interne.
  • Linux : nmcli con mod … ipv4.dns 192.168.50.10 ipv4.ignore-auto-dns yes ; resolvectl flush-caches.

7. Validation

nslookup sans serveur forcé répond ; ping www.google.be affiche « Envoi d'une requête 'ping' sur www.google.be [142.250.179.195] » ; nom interne résolu ; navigateur OK ; test sur un second poste si correction faite au DHCP.

8. Réponse d'examen modèle

Réponse rédigée attendue

« Le ping de la box (192.168.50.1) et de 8.8.8.8 répond : câble, adressage, passerelle et accès Internet fonctionnent. Le ping de www.exemple.be échoue avant tout envoi (“n'a pas pu trouver l'hôte”) : le nom n'est pas traduit en adresse. ipconfig /all montre le DNS 192.168.50.5, ancien serveur retiré ; nslookup vers ce serveur expire, alors que nslookup vers le serveur du réseau 192.168.50.10 renvoie l'adresse. Cause : DNS saisi manuellement et obsolète. Correction : DNS automatique (le DHCP distribue 192.168.50.10), ipconfig /renew et /flushdns. Vérification : nslookup et ping par nom réussissent, le site s'ouvre ; la mention “réponse ne faisant pas autorité” est normale. »

Perd des points : conclure « pas d'Internet » ; mettre 8.8.8.8 comme DNS sur un poste de domaine (les noms internes cassent, jonction et GPO échouent) ; interpréter « Réponse ne faisant pas autorité » comme une panne.

9. Pièges et variantes

Piège Un seul site KO avec nslookup OK et ping IP OK → le site, le proxy ou un filtrage, pas le DNS. Un nom interne court (srv01) peut échouer alors que le FQDN (srv01.entreprise.local) répond → suffixe DNS manquant (option DHCP « nom de domaine » ou suffixe de la connexion). Après changement de l'IP d'un serveur, les postes gardent l'ancienne adresse en cache : ipconfig /flushdns.

P3.8 — Plus aucun poste n'accède à Internet (panne générale)

Fréquence : fréquent · Gravité : forte (toute l'activité) — priorité haute

1. Symptômes observables

  • Tous les postes, filaires et Wi-Fi : « Pas d'accès Internet » ; le partage local et l'imprimante fonctionnent encore.
  • Box : voyant « Internet » / « DSL » / « Fibre » éteint, rouge ou clignotant ; voyant « LOS » rouge sur l'ONT fibre.

2. Causes possibles (classées)

  1. Panne ou maintenance du FAI, coupure de ligne (travaux).
  2. Box plantée (ne route plus) ou désynchronisée ; câble WAN / jarretière fibre / câble téléphonique débranché.
  3. Box remplacée/réinitialisée : identifiants de connexion non saisis.
  4. Abonnement suspendu (facture impayée) → page du FAI.
  5. Si la box ne répond même pas au ping : switch central sans courant, box éteinte.

3. Questions initiales et sécurité

  • « Depuis quand ? Orage, travaux, coupure de courant ? Quelqu'un a-t-il touché à la box ? » Relever les voyants AVANT tout redémarrage (preuve pour le FAI). Prévenir les utilisateurs de la coupure pendant le redémarrage. Ne jamais faire un reset usine (perte de configuration : redirections, Wi-Fi, DHCP) sans sauvegarde et accord.

4. Diagnostic pas à pas

  1. Sur un poste : ping 192.168.1.1 (box).

    SI pas de réponse sur tous les postes → box éteinte/plantée ou switch central : vérifier alimentation et voyants du switch, puis de la box.

    SINON (box OK) → étape 2.

  2. ping 8.8.8.8 + tracert -d 8.8.8.8.
    Détermination de l'itinéraire vers 8.8.8.8 avec un maximum de 30 sauts.

  1    <1 ms    <1 ms    <1 ms  192.168.1.1
  2     *        *        *     Délai d'attente de la demande dépassé.
  3     *        *        *     Délai d'attente de la demande dépassé.
  4     *        *        *     Délai d'attente de la demande dépassé.

    SI seul le saut 1 (box) répond → panne côté WAN/FAI : étape 3.

    SINON (s'arrête plus loin, ou 8.8.8.8 répond) → Internet par IP fonctionne : vérifier le DNS de la box (P3.7).

  3. Interface de la box (http://192.168.1.1) : état de la synchronisation / connexion, adresse IP WAN, journal.

    SI « non synchronisé » / pas d'IP WAN → vérifier câble WAN/fibre, page d'incidents du FAI (depuis un smartphone en 4G), redémarrer la box (après relevé).

    SINON (connectée mais pas de trafic) → redémarrage, puis escalade FAI.

5. Test de confirmation

Le premier saut répond, les suivants non, sur PLUSIEURS postes ; l'état WAN de la box est déconnecté ; le portail d'incidents du FAI signale la panne. Limite : certains routeurs du FAI ne répondent jamais au tracert (des « * » isolés au milieu d'une route qui aboutit ne sont pas une panne).

6. Correction

  • Rebrancher/réparer le câble WAN ; redémarrer la box (débrancher 30 s) ; ressaisir les identifiants de connexion fournis par le FAI.
  • Panne FAI : ouvrir un ticket (référence client, voyants relevés, heure de début), solution de secours (partage 4G) si l'activité l'exige ; informer les utilisateurs (→ Fiche 5 · Escalade).

7. Validation

Voyant Internet vert ; depuis deux postes (filaire et Wi-Fi) : ping 8.8.8.8, ping nom, navigation ; services dépendants (messagerie, VPN, imprimante cloud).

8. Réponse d'examen modèle

Réponse rédigée attendue

« Tous les postes sont touchés : je cherche une cause commune. Depuis le poste de l'accueil, la box 192.168.1.1 répond (le réseau local est sain), mais 8.8.8.8 ne répond pas ; tracert 8.8.8.8 s'arrête après le premier saut (la box). La panne est donc entre la box et Internet. Le voyant “Internet” de la box est rouge et l'interface indique “non synchronisé”. Je relève les voyants, je vérifie le câble de la ligne, puis je redémarre la box en prévenant les utilisateurs. Sans retour de la synchronisation, j'ouvre un ticket chez le FAI avec ces relevés. Validation : voyant vert, ping 8.8.8.8 et navigation depuis deux postes. »

Perd des points : diagnostiquer chaque poste un par un ; reset usine de la box ; conclure sur un seul poste.

9. Pièges et variantes

Piège Box fonctionnelle mais son serveur DNS en panne : 8.8.8.8 répond, les noms non, sur tous les postes → c'est P3.7 pour tous (corriger temporairement le DNS distribué). Panne « Internet » uniquement en Wi-Fi → P3.25. Box neuve : son réseau LAN par défaut (ex. 192.168.0.0/24) diffère de l'ancien (192.168.1.0/24) → les adresses fixes (imprimante, NAS) ne sont plus dans le bon réseau (voir Dossier 4).

P3.9 — Ping ou service bloqué par le pare-feu / profil réseau « Public »

Fréquence : très fréquent (deux PC en direct, partage) · Gravité : faible, mais induit en erreur

1. Symptômes observables

  • Ping d'un PC Windows allumé et bien adressé → « Délai d'attente de la demande dépassé ».
  • Partage / imprimante partagée inaccessible depuis un poste, réseau classé « Réseau public » (Paramètres → Réseau et Internet → Ethernet ou Wi-Fi → Type de profil réseau).

2. Causes possibles (classées)

  1. Profil réseau Public : règles « Partage de fichiers et d'imprimantes » et écho ICMP désactivées.
  2. Pare-feu tiers (antivirus) plus strict.
  3. Règle d'entreprise (stratégie de groupe).
  4. Hôte réellement absent (à distinguer !).

3. Questions initiales et sécurité

  • Ne jamais DÉSACTIVER le pare-feu comme correction : seulement comme test bref, sur réseau de confiance, puis le réactiver.

4. Diagnostic pas à pas

  1. ping de la cible puis arp -a.

    SI l'IP de la cible apparaît avec sa MAC → elle est présente sur le segment et a répondu à l'ARP : c'est l'ICMP qui est filtré.

    SINON → cible absente / autre réseau : revoir adressage, câble.

  2. Sur la cible : type de profil réseau (PowerShell : Get-NetConnectionProfile).

    SI NetworkCategory : Public → étape 3.

    SINON → règles de pare-feu (wf.msc) ou pare-feu tiers.

  3. Tester le service lui-même : Test-NetConnection 192.168.10.1 -Port 445 → TcpTestSucceeded : False/True.

5. Test de confirmation

Activer la règle (ou le profil Privé) → le ping répond immédiatement ; le désactiver → délai dépassé. Limite : un ping qui répond ne prouve pas que le port 445 (partage) est ouvert, et inversement.

6. Correction

  • Réseau de confiance : Type de profil réseau → Privé ; Paramètres réseau avancés → Paramètres de partage avancés → Activer la découverte du réseau et le partage de fichiers et d'imprimantes (profil Privé).
  • Ou règle ciblée : netsh advfirewall firewall set rule group="Partage de fichiers et d'imprimantes" new enable=yes (nom du groupe en français sur Windows FR) ; PowerShell : Set-NetConnectionProfile -InterfaceAlias "Ethernet" -NetworkCategory Private.

7. Validation

Ping OK, port 445 True, accès au partage ; le pare-feu reste ACTIF (vérifier « Pare-feu Windows Defender : activé »).

8. Réponse d'examen modèle

Réponse rédigée attendue

« Le ping de PC-ACCUEIL (192.168.10.1) répond “Délai d'attente de la demande dépassé” : la demande part (même réseau 192.168.10.0/24), mais aucune réponse ne revient. arp -a montre la MAC de PC-ACCUEIL : la machine est présente et a répondu à l'ARP, c'est donc son pare-feu qui bloque l'écho ICMP, la connexion étant classée “réseau public”. Je passe le profil en Privé (réseau de confiance) — sans désactiver le pare-feu — et le ping répond. »

Perd des points : « je désactive le pare-feu » comme solution définitive ; conclure « PC éteint » ou « câble HS » sur un délai dépassé sans autre test.

9. Pièges et variantes

Piège Une imprimante ou une box peut aussi ignorer le ping tout en imprimant. Inversement, un serveur qui répond au ping peut avoir le partage bloqué (port 445) → message « chemin réseau introuvable » et non « accès refusé » (P3.17).

P3.10 — Réseau lent, pertes de paquets, coupures intermittentes (filaire)

Fréquence : fréquent · Gravité : variable ; difficile car intermittent

1. Symptômes observables

  • Copies de fichiers lentes, visioconférence qui saccade, déconnexions de quelques secondes ; ping -t avec des « Délai d'attente » épisodiques ou des temps qui montent (1 ms → 300 ms).
  • État de la carte : vitesse 100 Mbit/s au lieu de 1 Gbit/s ; compteur d'erreurs.

2. Causes possibles (classées)

  1. Saturation : sauvegarde, mises à jour, téléchargement massif, Wi-Fi + filaire sur une liaison Internet faible.
  2. Câble/connecteur abîmé ou mal serti (paire défectueuse → repli à 100 Mbit/s, erreurs CRC).
  3. Négociation de vitesse/duplex incorrecte (duplex forcé d'un côté seulement).
  4. Boucle sur le réseau (tempête de diffusion) → P3.14.
  5. Conflit IP intermittent → P3.4 ; pilote/gestion d'énergie de la carte.
  6. Hub ancien (domaine de collision partagé) encore en place.

3. Questions initiales et sécurité

  • « À quels moments ? Tous les postes ou un seul ? Une activité particulière (sauvegarde à 12 h) ? » Noter les horaires pour corréler.

4. Diagnostic pas à pas

  1. ping -t 192.168.1.1 pendant quelques minutes (Ctrl+C → statistiques).
    Statistiques Ping pour 192.168.1.1:
    Paquets : envoyés = 300, reçus = 271, perdus = 29 (perte 9%),
Durée approximative des boucles en millisecondes :
    Minimum = 0ms, Maximum = 412ms, Moyenne = 23ms

    SI pertes vers la passerelle sur le LAN filaire → problème local (câble, port, carte, boucle, conflit) : étape 2.

    SINON (LAN propre, seul Internet lent) → saturation de la liaison Internet : mesurer le débit, identifier le gros consommateur.

  2. État de la connexion (ncpa.cpl → double-clic) : vitesse.

    SI 100 Mbit/s avec matériel Gigabit → câble/prise à tester (→ Fiche 3 · Testeur), changer le cordon, vérifier que le duplex est en « Négociation automatique » (Gestionnaire de périphériques → carte → Avancé → Speed & Duplex).

    SINON → étape 3.

  3. Comparer avec un autre poste sur le même switch et sur un autre switch ; observer les voyants du switch (clignotement frénétique et simultané de tous les ports = boucle/tempête).
  4. Gestion de l'alimentation de la carte (Gestionnaire de périphériques → Propriétés → Gestion de l'alimentation : décocher « Autoriser l'ordinateur à éteindre ce périphérique ») si coupures après inactivité.

5. Test de confirmation

Le défaut disparaît en changeant UN élément (cordon, port, duplex) et réapparaît en le remettant ; les pertes coïncident avec l'horaire d'une activité. Limite : intermittent = observer assez longtemps (au moins la durée habituelle entre deux coupures).

6. Correction

  • Remplacer le cordon, réparer la prise ; remettre la négociation automatique des deux côtés ; supprimer la boucle ; remplacer le hub par un switch ; planifier sauvegardes/mises à jour hors heures ; mettre à jour le pilote.

7. Validation

100 pings consécutifs sans perte, temps < 1–2 ms sur le LAN ; vitesse de liaison 1 Gbit/s ; copie d'un gros fichier au débit attendu ; suivi sur la période où le défaut apparaissait.

8. Réponse d'examen modèle

Réponse rédigée attendue

« Un ping continu vers la passerelle montre 9 % de pertes et des pics à 412 ms, uniquement sur ce poste filaire : le problème est local. La liaison est négociée à 100 Mbit/s alors que la carte et le switch sont Gigabit, signe d'une paire défectueuse. Je remplace le cordon de brassage : la liaison passe à 1 Gbit/s et 300 pings passent sans perte. Si le défaut persistait, je testerais la prise et le câble capillaire au testeur. »

Perd des points : conclure sur un seul ping de 4 paquets ; changer la configuration IP pour une lenteur.

9. Pièges et variantes

Piège « Lent » en Wi-Fi = autre procédure (P3.26). Lenteur à l'ouverture de session sur domaine = souvent DNS mal configuré (le poste cherche le DC via un DNS public), pas un débit. Lent vers un seul serveur = le serveur (disque, CPU), pas le réseau.

P3.11 — Configuration correcte mais rien ne fonctionne : pile TCP/IP, Winsock, proxy, VPN

Fréquence : rare à occasionnel · Gravité : bloquante pour le poste

1. Symptômes observables

  • ping 127.0.0.1 échoue, ou ipconfig correct + ping IP OK mais navigateurs/applis réseau KO.
  • Après désinstallation d'un antivirus/VPN, infection, ou « optimiseur » réseau.

2. Causes possibles (classées)

  1. Proxy configuré (Paramètres → Réseau et Internet → Proxy) — applis web KO, ping OK.
  2. Heure/date du PC fausse → erreurs de certificat HTTPS (« Votre horloge est en avance/retard »).
  3. VPN resté connecté / carte virtuelle prioritaire.
  4. Catalogue Winsock ou pile TCP/IP corrompu (127.0.0.1 KO).
  5. Malware (fichier hosts, proxy imposé).

3. Questions initiales et sécurité

  • « Qu'a-t-on installé/désinstallé récemment ? » Les réinitialisations effacent les réglages IP manuels : relever la configuration (ipconfig /all) AVANT.

4. Diagnostic pas à pas

  1. ping 127.0.0.1.

    SI échec → pile TCP/IP : étape 5 (correction).

    SINON → étape 2.

  2. Proxy : « Utiliser un serveur proxy » activé sans raison ? (netsh winhttp show proxy pour le proxy système).
  3. Date/heure et synchronisation (w32tm /query /status).
  4. Cartes virtuelles (ncpa.cpl) : VPN, TAP, Hyper-V ; route print : route par défaut via le VPN ?
  5. Analyse anti-malware et contrôle du fichier hosts.

5. Test de confirmation

Le symptôme disparaît après désactivation du proxy / correction de l'heure / déconnexion du VPN, ou après la réinitialisation de la pile. Limite : la réinitialisation corrige aussi d'autres choses — noter ce qui a été fait.

6. Correction

Attention netsh int ip reset et netsh winsock reset effacent les adresses IP fixes, DNS et certains réglages réseau ; logiciels VPN/pare-feu tiers éventuellement à réinstaller. Prérequis : ipconfig /all sauvegardé, droits admin, redémarrage possible. Alternative prudente d'abord : désactiver/réactiver la carte, retirer le proxy, mettre à jour le pilote. Windows 10/11 propose aussi Paramètres → Réseau et Internet → Paramètres réseau avancés → Réinitialisation du réseau (réinstalle les cartes, même effet + redémarrage).

C:\> netsh winsock reset
C:\> netsh int ip reset
C:\> ipconfig /flushdns
C:\> shutdown /r /t 0

7. Validation

Ressaisir la configuration fixe éventuelle ; ping 127.0.0.1, passerelle, 8.8.8.8, nom ; navigation HTTPS sans alerte ; VPN qui se connecte/déconnecte correctement.

8. Réponse d'examen modèle

Réponse rédigée attendue

« Le ping de 127.0.0.1 échoue : la pile TCP/IP du poste elle-même est défaillante, indépendamment du câble et du réseau. Après avoir relevé la configuration (ipconfig /all), j'exécute en administrateur netsh winsock reset et netsh int ip reset, puis je redémarre. Je ressaisis la configuration fixe relevée, puis je refais la chaîne de tests : 127.0.0.1, propre IP, passerelle, 8.8.8.8 et un nom. »

Perd des points : dire que ping 127.0.0.1 OK prouve que « la carte et le câble fonctionnent » (il ne teste ni l'un ni l'autre).

9. Pièges et variantes

Piège Linux : ping 127.0.0.1 KO = interface lo DOWN (sudo ip link set lo up). Un ping vers sa PROPRE IP qui répond ne teste pas non plus le câble (la réponse ne sort pas du poste).
