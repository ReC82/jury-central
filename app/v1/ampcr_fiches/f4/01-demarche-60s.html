1. Face à un problème réseau : la démarche en 60 secondes

  1. Délimiter le périmètre (10 s) — UN poste ou TOUS les postes ? Filaire, Wi-Fi ou les deux ? Tout Internet, un seul site, un nom interne, un partage, une imprimante ? Depuis quand, après quel changement (nouvelle box, déménagement de bureau, mise à jour, nouveau mot de passe Wi-Fi, poste neuf) ?

    SI tous les postes sont touchés → la cause est COMMUNE : box/FAI, switch, serveur DHCP/DNS, contrôleur de domaine, serveur de fichiers. Commence par l'équipement partagé.

    SINON (un seul poste) → la cause est LOCALE : câble/prise/port, carte, configuration IP, pare-feu, profil réseau, compte, profil Wi-Fi. Compare avec un poste qui fonctionne.

  2. Regarder avant de taper (10 s) — icône réseau (globe barré, croix rouge, triangle « Pas d'accès Internet »), voyants de la carte et du port de switch, état du Wi-Fi (SSID connecté, barres de signal).

    SI pas de voyant de lien / « Câble réseau non connecté » → couche physique : P3.1 puis → Fiche 3 · Testeur.

    SINON lien présent → passe à la configuration IP.

  3. Lire la configuration IP (15 s) — ipconfig /all (Windows) ou ip addr + ip route + resolvectl status (Linux). Lire dans l'ordre : adresse, masque, passerelle, DNS, DHCP activé, bail, adresse physique.

    SI 169.254.x.x → P3.2 DHCP ; adresse « (Doublon) » → P3.4 ; masque différent des autres postes → P3.5 ; passerelle vide ou hors réseau → P3.6 ; DNS inconnu → P3.7.

    SINON configuration cohérente → tests en couches.

  4. Tester en couches, du plus proche au plus loin (20 s) — 127.0.0.1 → propre IP → passerelle → IP publique (8.8.8.8 ou 1.1.1.1) → nom DNS. Le PREMIER test qui échoue localise la panne (détail en 1 bis).
  5. Confirmer, corriger, revalider (5 s de réflexion) — une hypothèse n'est retenue qu'après un test discriminant ; après correction, refaire TOUTE la chaîne de tests + le test métier de l'utilisateur (ouvrir le site, le partage, imprimer une page) et consigner avant/après.

Piège Un ping qui échoue n'est PAS une preuve de panne : beaucoup d'hôtes (PC Windows en profil Public, serveurs, certains routeurs) bloquent l'écho ICMP. Confirme toujours par un second test (arp -a après le ping, Test-NetConnection sur le port du service, accès réel).

1 bis. L'ordre des tests et l'interprétation de chaque résultat

Pose toujours les tests dans cet ordre. Exemple de réseau : poste 192.168.1.25/24, passerelle (box) 192.168.1.1, DNS 192.168.1.1.

Lire précisément la réponse d'un ping (Windows en français)

Message affichéCe qui s'est passéConclusion pratique
« Réponse de 192.168.1.1 : octets=32 temps<1ms TTL=64 »Aller-retour réussi.Couche 3 OK jusqu'à la cible. TTL 128 ≈ Windows, 64 ≈ Linux/box, 255 ≈ équipement réseau (indice, pas preuve).
« Délai d'attente de la demande dépassé. »La demande est partie (le poste savait où l'envoyer), aucune réponse dans le délai (4 s par défaut).Cible éteinte, pare-feu qui bloque l'ICMP, réponse perdue (route retour), câble coupé plus loin. Faire arp -a : si la MAC de la cible est apprise, la cible est présente et filtre le ping.
« Réponse de 192.168.1.25 : Impossible de joindre l'hôte de destination. » (ancien libellé : « Hôte de destination inaccessible »)La réponse vient de TA PROPRE adresse : ton poste a tenté une requête ARP pour la cible (même réseau) et personne n'a répondu.Cible absente du segment : éteinte, débranchée, adresse changée (imprimante passée en DHCP), autre VLAN, ou adresse mal tapée.
« Réponse de 192.168.1.1 : Impossible de joindre l'hôte de destination. »La réponse vient de la PASSERELLE : elle a reçu ton paquet mais ne sait pas joindre la cible (ARP sans réponse de son côté, pas de route).Ton poste et ta passerelle fonctionnent ; le problème est derrière la passerelle (autre sous-réseau, hôte distant éteint, route manquante sur le routeur).
« PING : échec de la transmission. Défaillance générale. »Le paquet n'a même pas pu partir.Pas de route (passerelle absente pour une cible distante), interface désactivée, pare-feu/antivirus local qui bloque, VPN cassé.
« La requête Ping n'a pas pu trouver l'hôte www.x.be. Vérifiez le nom et essayez à nouveau. »Résolution de nom impossible : aucun paquet ICMP envoyé.Problème DNS (ou nom mal orthographié) : ce n'est PAS une preuve de coupure Internet.
« Le délai de vie (TTL) a expiré lors du transit. »Le paquet a tourné jusqu'à TTL 0.Boucle de routage (deux routeurs qui se renvoient le paquet) : cas rare, à escalader.
Linux : « ping: connect: Network is unreachable »Le noyau n'a aucune route pour la cible : rien n'est émis.Route par défaut manquante (ip route sans ligne default via) ou interface DOWN.
Linux : « From 192.168.1.25 icmp_seq=1 Destination Host Unreachable »Équivalent Linux de « Impossible de joindre l'hôte » (ARP sans réponse).Cible absente du segment local.
Linux : « ping: www.x.be: Temporary failure in name resolution » / « Name or service not known »DNS injoignable / nom inexistant.Problème de résolution DNS.
Réponses alternées avec délais / « perdus = 2 (50 % de perte) »Liaison instable.Câble/connecteur abîmé, Wi-Fi faible ou brouillé, port en duplex incorrect, saturation : ping -t prolongé + comparaison filaire/Wi-Fi.

Réponse rédigée attendue (formulation type d'un test)

« J'exécute ping 192.168.1.1 pour vérifier la liaison avec la passerelle. Résultat : 4 réponses, 0 % de perte. Interprétation : le câble, la carte réseau, l'adressage et le réseau local fonctionnent jusqu'à la box. La panne se situe donc au-delà : j'exécute ensuite ping 8.8.8.8 pour tester l'accès Internet par adresse. »

Perd des points : enchaîner les commandes sans écrire ce que chaque résultat prouve ; conclure « Internet est coupé » sur un ping de nom qui échoue ; confondre « Délai d'attente » et « Impossible de joindre l'hôte » ; ne pas préciser QUI répond (ta propre IP ou la passerelle).
