# Ticket #39 — Comptes V1 : authentification utilisateur et rôles extensibles

**Date** : 2026-09-17
**Branche** : `feature/39-v1-auth`

---

## 1. Audit initial

Voir `docs/auth_v1.md`, § 2, pour le détail. Résumé des constats déterminants :

- `app/auth.py`/`app/admin.py` : l'admin utilise déjà une session cookie signée
  (`starlette.middleware.sessions.SessionMiddleware`, `itsdangerous`, déjà une
  dépendance) — mécanisme réutilisé tel quel pour V1, pas un second système de session.
- **Aucun mécanisme CSRF n'existe nulle part dans le projet** avant ce ticket (recherché
  explicitement, aucune occurrence) : ce ticket introduit le premier, pas un concurrent.
- Aucune bibliothèque de hachage de mot de passe installée.
- `app/database.py::ensure_schema_migrations` gère déjà l'ajout additif de colonnes
  (pattern du ticket #22, `lesson_blocks.space`) — directement réutilisable pour
  `v1_users`.
- `app/v1/models.py::User` (ticket #38) existait déjà avec `email`/`display_name`/
  `role`/`plan`/`is_active`, sans champs d'authentification.
- `app/templating.py` n'avait pas de `context_processors` — mécanisme Starlette natif,
  utilisé pour exposer `current_user`/`csrf_token` à toutes les pages sans modifier
  chaque route.
- Audit des routes PRACTICE/EXAM existantes (`app/main.py`, `app/practice.py`) :
  `/uaa/{slug}/practice`/`/uaa/{slug}/exam` sont déjà génériques (filtrage par
  `BlockSpace`, pas par cours). Audit de `app/seed.py` : seuls les blocs
  `editorial_exercise`/`ai_exercise` existent en espace PRACTICE/EXAM aujourd'hui (12
  `EDITORIAL_EXERCISE` + 3 `AI_EXERCISE`, 0 `QUIZ`/`GENERATED_EXERCISE`/`EXERCISE`) — les
  routes `/practice/api/generate`, `/practice/api/verify`, `/practice/api/reveal`,
  `/practice/api/value-table/verify`, `/practice/api/quiz/{block_id}/verify` et
  `/practice/equations` sont donc confirmées hors périmètre (démo/legacy indépendants de
  la hiérarchie Subject/Module/UAA), non protégées par ce ticket.

---

## 2. Solution retenue

Détaillée et justifiée dans `docs/auth_v1.md`. Résumé des décisions :

- **Session** : cookie signé existant (`SessionMiddleware`), pas de table de sessions
  persistées — un seul mécanisme de session dans toute l'application.
- **Mot de passe** : Argon2id via `argon2-cffi` (nouvelle dépendance) — recommandation
  OWASP actuelle, aucun algorithme réimplémenté.
- **CSRF** : synchronizer token stocké dans la session déjà signée, appliqué aux 3
  routes de mutation V1 (`/register`, `/login`, `/logout`), jamais rétrofité sur l'admin
  existant (hors périmètre).
- **Rôles/plans** : restent des enums Python (`UserRole`/`UserPlan`, ticket #38,
  inchangés), cohérent avec la convention déjà établie du projet
  (`BlockType`/`BlockSpace`).
- **`require_user` (page HTML, redirige) vs `require_user_api` (API JSON, 401)** :
  deux dépendances distinctes car une redirection 303 vers `/login` serait silencieusement
  suivie par un appel `fetch()` et casserait le parsing JSON côté client — voir
  `docs/auth_v1.md`, § 7.

## 4. Migrations

`app/database.py::ensure_schema_migrations` étendu (refactorisé en un helper générique
`_add_column_if_missing(table, column, ddl_type)`, réutilisé pour les 3 colonnes gérées
à ce jour) : ajoute `v1_users.password_hash` (nullable) et `v1_users.last_login_at`
(nullable) si la table existe déjà sans ces colonnes (cas d'un staging seedé au ticket
#38). Idempotent, strictement additif, aucun `reset-db`. Testé explicitement (§ 6,
scénarios 20/21).

---

## 5. Sécurité

- **Mots de passe** : jamais stockés en clair (`User.password_hash` uniquement, encodé
  Argon2id) ; comparaison en temps constant intégrée à `argon2-cffi` ; défense de timing
  supplémentaire sur email inconnu (hachage factice, voir `docs/auth_v1.md` § 4).
- **Login** : message générique unique pour email inconnu / mauvais mot de passe /
  compte inactif — aucune distinction observable.
- **Session** : régénérée (`request.session.clear()`) à chaque connexion réussie —
  limite la fixation de session.
- **Cookie** : HttpOnly (toujours), SameSite=Lax (défaut), Secure conditionnel à
  `APP_ENV` (voir § 7, incident).
- **Open redirect** : `safe_next_path` rejette tout `next` qui n'est pas un chemin local
  strict (`/...`) — teste explicitement `https://`, `//`, `\`, `javascript:`.
- **CSRF** : voir § 1/2 — jeton en session, comparaison en temps constant.
- **API JSON protégées** : `require_user_api` retourne 401 JSON, jamais une redirection
  qu'un `fetch()` suivrait silencieusement.

## 7. Incident détecté et corrigé pendant ce ticket : `APP_ENV` non isolé en test

Ajouter `https_only=settings.app_env in ("staging", "prod")` sur `SessionMiddleware` a
cassé silencieusement **67 tests** (admin ET V1, tout ce qui dépend de deux requêtes
successives avec cookie) : le vrai `.env` de ce serveur porte déjà `APP_ENV=staging`
(réglage légitime pour le déploiement réel, indépendant de ce ticket), et
`tests/conftest.py` ne forçait jusqu'ici que `OPENAI_API_KEY=""` — sans protection
équivalente pour `APP_ENV`, la suite de tests lisait silencieusement cette valeur
`staging` depuis le vrai `.env`, activant `https_only=True`. `TestClient` n'utilisant
jamais HTTPS, le cookie `Secure` posé par la première réponse (login/register) n'était
alors plus jamais renvoyé par le client sur la requête suivante — exactement la même
classe de bug que l'incident `OPENAI_API_KEY` déjà documenté aux tickets #29/#35, cette
fois sur une variable de configuration que je venais moi-même d'introduire sans
généraliser la même discipline.

**Corrigé** : `tests/conftest.py` force désormais `os.environ["APP_ENV"] = "local"`
(même mécanisme, même commentaire explicatif que pour `OPENAI_API_KEY`).
`app/safe_local_server.py` (ticket #35) reçoit la même protection pour les vérifications
manuelles locales. Après correction : 48 échecs restants (uniquement les tests appelant
directement les routes désormais protégées, tous corrigés ensuite — voir § 8), confirmant
que cet incident expliquait bien les 19 échecs « inattendus » (admin, value-table) qui
n'avaient aucun rapport apparent avec l'ajout de `require_user`.

**Second incident, sans rapport avec le code de ce ticket, également corrigé** :
pendant le développement, deux commandes `python -c "import app.main"` lancées sans
`DATABASE_URL` isolé (pour une simple vérification de syntaxe/chargement) ont, par
défaut, pointé vers la vraie `jury_central.db` et déclenché `Base.metadata.create_all()`
dessus, créant silencieusement les 17 tables V1 vides du ticket #38 (déjà remédié une
fois lors du ticket #38, la leçon n'avait pas empêché la récidive). Détecté chaque fois
immédiatement, vérifié que les 17 tables créées étaient vides (0 ligne) et que les 4
tables historiques restaient intactes (subjects=2, modules=4, uaas=5,
lesson_blocks=140), puis les 17 tables ont été supprimées (`DROP TABLE`) pour restaurer
l'état exact d'avant ce ticket. Aucune donnée perdue ni altérée à aucun moment. Un
retour d'expérience a été journalisé (outil interne de feedback) pour généraliser cette
discipline au-delà de `OPENAI_API_KEY`/`APP_ENV` à toute commande manuelle sur ce
serveur.

## 8. Tests

**Mise à jour de 8 fichiers de tests existants** (35 appels directs aux 3 routes API
désormais protégées + plusieurs appels aux pages `/practice`/`/exam` désormais
protégées) : `tests/test_practice_editorial_routes.py`, `tests/test_practice_ai_routes.py`,

`tests/test_ticket17_no_regression.py`, `tests/test_ticket21_no_regression.py`,
`tests/test_ticket22_no_regression.py`, `tests/test_ticket37_mc01_practice_order.py` —
chaque appel désormais protégé passe par la nouvelle fixture `authenticated_client`
(`tests/conftest.py`), qui inscrit puis connecte un compte de test réel via les vraies
routes `/register` (même approche que `admin_client`, qui utilise la vraie route
`/admin/login`). Aucun de ces tests n'a changé d'assertion fonctionnelle — seul le moyen
d'accès à la route a changé (authentifié plutôt qu'anonyme), cohérent avec la nouvelle
règle produit.

**`tests/test_ticket39_v1_auth.py`** (29 tests) couvre les 22 scénarios minimaux
demandés :

1. Inscription réussie.
2. Mot de passe jamais stocké en clair (hash Argon2id vérifié, chaîne brute absente).
3. Email dupliqué refusé (1 seule ligne en base après tentative).
4. Email normalisé (stockage en minuscules + reconnexion avec casse différente ; test
   unitaire de `normalize_email`).
5. Mot de passe incorrect refusé (401, message générique).
6. Utilisateur inactif refusé (même message générique que § 5 — aucune distinction).
7. Login réussi (session établie, `/account` accessible ensuite).
8. Logout invalide la session (`/account` redirige après déconnexion).
9. Cookie de session : HttpOnly + SameSite=Lax présents, Secure absent (APP_ENV=local en
   test).
10. Open redirect rejeté (`next` externe ignoré au profit de `/`, plus test unitaire de
    `safe_next_path` couvrant `https://`, `//`, `javascript:`, etc.).
11. CSRF sur inscription/connexion (400 si jeton invalide) et déconnexion (no-op sûr si
    jeton invalide, session conservée).
12. Cours accessible anonymement.
13. Practice inaccessible anonymement (303 vers `/login?next=...`).
14. Exam inaccessible anonymement (idem).
15. Practice accessible connecté ; exam accessible connecté (bonus, cohérence).
16. Plusieurs utilisateurs isolés (comptes distincts, aucune fuite d'email entre
    sessions).
17. Rôle par défaut `student`.
18. Plan par défaut `free`.
19. Helpers de rôle (`require_role` accepte le rôle attendu, lève 403 sinon — testé
    directement, sans route HTTP dédiée puisqu'aucune n'existe encore).
20. Migration additive sur une table `v1_users` reconstituée dans son état pré-#39
    (colonnes ajoutées, ligne existante intacte, nouvelle colonne `NULL` plutôt qu'une
    valeur inventée).
21. Second passage de la migration idempotent (pas d'erreur, colonnes non dupliquées).
22. Admin HTTP existant non régressé (`admin_client` fonctionne toujours ; bonus : une
    session V1 ne donne jamais accès à `/admin/*`).
